## Basic Usage

Add functions directly as tools:

```python
def get_weather(location: str) -> str:
    """Get weather for a location."""
    return f"Weather in {location}: 22°C"

agent = Agent(
    name="weather_agent",
    model="openai/gpt-4o-mini",
    tools=[get_weather]  # Function automatically becomes a tool
)
```

## Sandboxed Python with Modal

`RunPython` executes Python in a fresh Modal sandbox for each call. Install the
optional dependency and configure Modal authentication on the machine running Timbal:

```bash
pip install 'timbal[modal]'
modal setup
```

In deployments, use Modal's `MODAL_TOKEN_ID` and `MODAL_TOKEN_SECRET` environment
variables instead. These authenticate the host SDK; they are not forwarded to the sandbox.

```python
from timbal.tools import RunPython

run_python = RunPython(dependencies=["numpy==2.2.6"], timeout=60)
result = await run_python(
    code="import numpy as np\nprint('Calculated mean')\nfloat(np.mean([1, 2, 3]))"
).collect()
# result.output:
# {"stdout": "Calculated mean\n", "stderr": "", "returncode": 0,
#  "return_value": 2.0, "status": "success", "error": None,
#  "artifacts": [], "artifact_error": None}

# Or pass the same tool to an Agent:
# Agent(..., tools=[run_python])
```

The final expression becomes `return_value`; top-level `await` works too. Values
that cannot be represented as JSON use their Python representation. Python errors
are returned in `error` with a type, message, and traceback. Setup/API failures
surface through Timbal's usual tool error handling.

Hard process exits return an `ExecutionError` alongside captured stdout, stderr,
and the exit code. Missing or malformed results are distinguished from oversized
results. Cleanup failures are logged without replacing completed results. Caller
cancellation waits for sandbox termination to finish or reach its cleanup deadline
before propagating; the provider lifetime limit remains the fallback.

Supply pip requirements through the tool's `dependencies` configuration or the
per-call `dependencies` argument. Configured requirements are authoritative:
per-call requests may omit them, repeat the same constraints, or add extras, but
cannot replace their versions, sources, or markers. Different constraints for the
same package are rejected before building, even if potentially compatible. Package
names are normalized, and new packages can be added per call. Imports are not
automatically converted to package names. Modal builds and caches the dependency image.

### File inputs and artifacts

Pass `files` as a mapping of relative filenames to file URLs, data URLs, or
application-supplied Timbal `File` objects. Inputs are copied into
`/workspace/inputs/<filename>`. Python runs with `/workspace` as its working
directory. Write deliverables under `/workspace/outputs`; the tool exports regular
files there, including nested directories, before terminating the sandbox.

```python
from pathlib import Path
from timbal.tools import RunPython
from timbal.types import File

run_python = RunPython()
result = await run_python(
    files={"sales.csv": File(Path("sales.csv"))},
    code="""
import csv
from pathlib import Path

with Path('inputs/sales.csv').open() as source:
    total = sum(float(row['amount']) for row in csv.DictReader(source))
Path('outputs/summary.txt').write_text(f'Total sales: {total}')
total
""",
).collect()

artifact = result.output["artifacts"][0]
# {"name": "summary.txt", "size": ..., "content_type": "text/plain", "file": ...}
# The file reference is a platform URL when platform storage is configured,
# or a local temporary-file path otherwise. It survives sandbox termination.
report = File(artifact["file"])
await report.load()
print(report.read().decode())
```

Agents pass file URLs from the conversation, for example
`files={"sales.csv": "https://example.com/sales.csv"}`. Raw host paths are rejected;
application code must explicitly wrap local files in `File`. File downloads happen
on the host and uploads use Modal's API, so `block_network=True` still allows file
transfer while blocking outbound connections from executed Python. Only supplied
files are copied; credentials and host directories are not mounted.

URL downloads accept only public Internet destinations. Every DNS answer and
redirect target is checked; loopback, private networks, cloud metadata, and
special-purpose addresses are rejected before connecting. Connections use a
validated IP with the original HTTPS hostname, preventing DNS rebinding while
retaining certificate verification. Downloads ignore environment proxies, reject
URL credentials, and follow at most five redirects. For private-source files,
application code can fetch them through its own authorized integration and pass
the contents as `File` objects.

`artifacts` contains file references and metadata, not base64 blobs in the model's
context. To reuse an artifact in a later call, pass its URL as another input, or
wrap its local reference in `File` from application code. Each call still starts
with a fresh sandbox.

The defaults are `max_files=20` and `max_file_bytes=10_000_000`, applied separately
to the input and output totals. `transfer_timeout=60` bounds input loading,
sandbox upload, and artifact retrieval separately. Filenames must be relative,
use forward slashes, and fit within 240 UTF-8 bytes. Output scanning is limited to
1000 directory entries; symlinks and special files are rejected. Output files are
read with byte limits even if background processes keep writing.

Completed executions export files even when Python raises an exception or exits
with a nonzero code. Execution timeouts and cancellation do not export files.
If export fails or exceeds a limit, `artifacts` is empty and `artifact_error`
explains the failure. The status is `error`, while stdout, stderr, return value,
and any original Python error remain available. Files are exported as observed;
finish writing them before the code returns. Invalid inputs and upload/API failures
use Timbal's normal tool error handling.

### System packages and browser setup

Use `system_dependencies` for Debian apt packages and `setup_commands` for trusted
image-build commands. The build order is **apt packages → Python packages → setup
commands**. All steps run on Modal. No system packages are installed on the host.

```python
run_python = RunPython(
    dependencies=["playwright==1.58.0"],
    system_dependencies=["fonts-dejavu-core"],
    setup_commands=["playwright install --with-deps chromium"],
    description=(
        "Run Python with Playwright and preinstalled Chromium. Use async Playwright APIs."
    ),
    block_network=False,  # Enable access to external websites at runtime.
    memory=1024,
    setup_timeout=600,
)
```

The setup command installs Chromium and its required Linux libraries. Pinning
Playwright keeps its Python package and downloaded browser aligned. Commands run
again when the relevant cached image layers change. Treat setup commands as trusted
developer configuration; they are not agent-call parameters. Build-time network
access is separate from the sandbox's runtime `block_network` policy.

The agent supplies `code`, optional `dependencies`, and optional `files`. Its description
includes configured Python/system packages, the execution timeout, and the actual
network policy. Use `description` to explain capabilities installed by arbitrary
setup commands, such as Chromium; command contents are not shown to the agent.

Network access is blocked by default (`block_network=False` enables it). Dependencies
are installed during image building, before that execution policy applies. CPU and
memory are bounded by `cpu` (cores, default 1) and `memory` (MiB, default 512).
`timeout` bounds execution, `setup_timeout` bounds setup (default 300 seconds), and
result retrieval and cleanup each have a 30-second deadline. The provider also
enforces a sandbox lifetime limit if the host disconnects.

`max_output_chars` bounds each captured output stream (default 20,000), retaining
its beginning and end. `max_result_bytes` bounds the result envelope (default
1,000,000); exceeding it produces an `OutputLimitError`. Source code is limited to
100,000 UTF-8 bytes.

Calls do not share variables or sandbox files; exported artifacts can be supplied
explicitly to later calls. This tool does not mount the host filesystem or expose
Timbal tools inside Python. It always uses Modal, with no local execution fallback.
Shared remote filesystems and persistent workspaces are separate concerns.

## Tool Configuration

Use the `Tool` type for custom descriptions and parameter control. The `handler` parameter is required and must be the function:

```python
from timbal import Tool

agent = Agent(
    name="weather_agent",
    model="openai/gpt-4o-mini",
    tools=[Tool(handler=get_weather)]
)
```

### Custom Description

If the function name or docstring doesn't clearly describe what the tool does, add a custom `description`. This is the description the LLM sees about the tool:

```python
Tool(
    handler=get_weather,
    description="Get current weather information for any location"
)
```

### Parameter Visibility

When a tool has many parameters, reduce tokens and avoid overwhelming the LLM by showing only required parameters:

```python
Tool(
    handler=search,
    schema_params_mode="required"  # Only show required params (default: "all")
)
```

You can also include or exclude specific parameters to fine-tune what the LLM sees:

```python
# Include extra parameters even in "required" mode
Tool(
    handler=search_function,
    schema_params_mode="required",
    schema_include_params=["model"]  # Include this optional param
)

# Exclude sensitive or internal parameters
Tool(
    handler=api_function,
    schema_exclude_params=["api_key", "debug_mode"]  # Hide from LLM
)
```

### Default Parameters

Set default values that are automatically applied when the tool is called. These values are used when not specified by the LLM:

```python
Tool(
    handler=database_query,
    default_params={
        "timeout": 30
    }
)
```

You can also use functions or environment variables as default parameters:

```python
def get_current_timestamp():
    return datetime.now().isoformat()

def process_data(data: str, timestamp: str | None = None, user_id: str = "default"):
    return f"Processed {data} at {timestamp} by {user_id}"

# Tool with dynamic default parameters
tool = Tool(
    name="data_processor",
    handler=process_data,
    default_params={
        "timestamp": get_current_timestamp,
        "user_id": "system_user"
    }
)
```

## Built-in Tools

Timbal provides built-in tools for common use cases. These tools are ready to use and don't require implementing handlers.

### WebSearch

`WebSearch` enables agents to search the web. 

<Warning>
`WebSearch` only works with **OpenAI** and **Anthropic** models. It's a specification-only tool that defines the tool schema for the LLM but doesn't contain executable logic. The actual web search execution is handled by the model provider. Other model providers are not supported.
</Warning>

```python
from timbal import Agent
from timbal.tools import WebSearch

agent = Agent(
    name="research_agent",
    model="openai/gpt-4o-mini",
    tools=[
        WebSearch(
            allowed_domains=["wikipedia.org", "github.com"],  # Restrict to specific domains
            user_location={
                "type": "approximate",
                "country": "US",
                "city": "New York"
            }  # Localize results
        )
    ]
)
```

Available options:
- `allowed_domains`: List of domains to restrict searches to
- `blocked_domains`: List of domains to exclude (Anthropic only)
- `user_location`: Dictionary with location info to localize search results. Must include `type` field. Common values are `"approximate"` or `"exact"`, but valid values depend on the provider.

#### Multiple Instances of the Same Tool

If you need multiple instances of the same built-in tool with different configurations, they will have the same name by default, which causes conflicts. Set unique names and descriptions for each instance:

```python
general_search = WebSearch()
general_search.name = "general_search"
general_search.description = "Search the web for general information."

domain_search = WebSearch(allowed_domains=["example.com"])
domain_search.name = "domain_search"
domain_search.description = "Search only within example.com domain."

agent = Agent(
    name="research_agent",
    model="anthropic/claude-opus-4-6",
    tools=[general_search, domain_search]
)
```

## Agent as a Tool

You can use an Agent as a tool within another Agent, enabling hierarchical agent compositions where specialized agents handle specific tasks.

Since `Agent` instances can be treated as `Tool` objects, they inherit the same parameter control configurations available to regular tools.

```python
from timbal import Agent

def calculate_cost(days: int, hotel_rate: float, flights: float = 0) -> float:
    """Calculate total trip cost."""
    return (days * hotel_rate) + flights

# Pricing specialist agent
pricing_agent = Agent(
    name="pricing_calculator",
    description="Calculate travel costs",  # Tool description for other agents
    model="openai/gpt-4o-mini",
    system_prompt="Answer only with the price. Any text",
    tools=[calculate_cost]
)

# Main travel agent
travel_agent = Agent(
    name="travel_assistant", 
    model="openai/gpt-4o",
    system_prompt="Help plan trips and provide travel advice.",
    tools=[pricing_agent]
)
```

<Note>
**Automatic Nesting:** When an agent is used as a tool within another agent (as shown above), it's automatically nested for proper tracing and context management. However, if you use an agent inside a `pre_hook` or `post_hook`, you must manually call `.nest()`. See [Using Agents in Hooks](/core-concepts/context#using-agents-in-hooks) for details.
</Note>

### Pinning results against compaction

Some tool results are durable context the model must keep referencing (loaded policy docs, skill guidance). Opt in with `pin_result=True` — [memory compaction](/agents/memory-compaction) never drops or truncates those results, and [tool result offloading](/agents/memory-compaction#tool-result-offloading) skips them too:

```python
Tool(
    handler=load_policy,
    pin_result=True,  # survive compaction for the life of the conversation
)
```

The built-in `read_skill` tool sets this automatically. See [Pinned results](/agents/memory-compaction#pinned-results).

### Limiting oversized results

When a tool can return huge payloads, set a per-tool size limit. Results over the threshold are spilled to a store (or truncated) **once, when produced**, before they enter memory:

```python
from timbal.core import ToolResultLimit, Truncate

Tool(
    handler=run_tests,
    result_limit=ToolResultLimit(threshold=8_000, action=Truncate(strategy="tail")),
)

Tool(
    handler=load_policy,
    result_limit=None,  # exempt — never reduced
)
```

An agent-wide default is `Agent(tool_result_limit=...)`. Precedence: `Tool.result_limit` > agent default. See [Tool Result Offloading](/agents/memory-compaction#tool-result-offloading).

## Commands

Register a `command` on any tool, agent, or workflow to let users invoke it directly with a `/` prefix — bypassing the LLM for that turn:

```python
Tool(handler=get_weather, command="weather")

# User sends: /weather Barcelona
# → runs get_weather(location="Barcelona") directly
```

See [Commands](/agents/commands) for argument parsing, nested agents, and workflows.

## MCP Servers

Connect any [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro) server and use its tools like native ones:

```python
from timbal import Agent
from timbal.core import MCPServer

agent = Agent(
    name="my_agent",
    model="openai/gpt-4o-mini",
    tools=[
        MCPServer(
            name="filesystem",
            transport="stdio",
            command="npx",
            args=["-y", "@modelcontextprotocol/server-filesystem", "."],
        ),
    ],
)
```

The server's tools are discovered at runtime and offered to the LLM alongside your other tools. See [MCP Servers](/agents/mcp) for transports, authentication, result handling, and connection lifecycle.

## Dynamic Tools

When tool availability depends on runtime conditions (user role, permissions, input parameters), you need dynamic tool resolution.

Instead of exposing all tools to the agent, use Timbal's `ToolSet` class to resolve which tools are available at runtime.

For example, with a role-based ToolSet:

- **Role: admin** → Available tools: `delete_user`, `modify_permissions`, `view_profile`
- **Role: user** → Available tools: `view_profile`

The ToolSet checks the role at runtime and returns only the relevant tools. The agent only has access to the tools returned by the ToolSet for that role. Users without admin role won't see admin tools, preventing the agent from attempting unauthorized actions.

See [Dynamic Agents](/agents/dynamic#dynamic-tools) for implementation details and examples.



## Summary

- **Automatic Introspection**: Function signatures become tool schemas automatically
- **Enhanced Validation**: Pydantic-based parameter validation
- **Execution Flexibility**: Support for all Python callable types
- **Better Configuration**: Fine-grained parameter control
- **Performance**: Concurrent execution and optimized patterns
- **Robustness**: Improved error handling and tracing
- **Tool Sets**: Dynamic tool resolution
- **MCP Servers**: Any Model Context Protocol server as a tool source — see [MCP Servers](/agents/mcp)
- **Commands**: Slash-command shortcuts for direct tool invocation — see [Commands](/agents/commands)

For more advanced patterns, see [Dynamic Agents](/agents/dynamic) and explore the built-in tools in the Timbal library.
