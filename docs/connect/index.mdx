title: "Timbal Connect"
description: "Timbal's on-premises data gateway: use databases and file shares on your own network from Timbal, without opening inbound ports"
---

Timbal Connect is Timbal's **on-premises data gateway**: a service you install on a server inside your network that acts as a bridge between your databases and file shares and Timbal. It opens one outbound, encrypted connection to Timbal and waits for instructions: browse a schema, run a read-only query, sync a table into a knowledge base, or copy files.

You never open an inbound port, and **database credentials never leave the server**. Timbal only knows each connection by the name you give it; the connection string lives in a file on the server.

## How it works

1. You create an **enrollment token** in Timbal: a single-use key, valid for 24 hours by default, that lets one server register itself.
2. You run the installer on the server. It checks the network path, downloads the connector, and registers it as a system service (a Windows service, a systemd unit or a launchd job).
3. On first start the connector trades the token for its own credential and connects. The token is consumed and can't be reused.
4. You list your databases in a local `connections.json` file, and any file shares in `config.json`. From then on, Timbal can use them by name.

The connector updates itself when Timbal pushes a new version, and rolls back automatically if the new version can't connect.

## What it can reach

| Source | Notes |
| ------ | ----- |
| PostgreSQL | Any version with a standard wire protocol |
| SQL Server | SQL logins, Windows-integrated authentication and NTLM, named instances |
| MySQL / MariaDB | Standard user/password |
| File shares | Local or mounted directories you list in [`config.json`](/connect/connections#file-shares) |

Supported platforms: Windows Server 2016 or newer (x64 and ARM64), Linux (x86_64 and aarch64, any distribution) and macOS (Intel and Apple silicon).

## Coming from the Power BI gateway?

If you've set up Microsoft's on-premises data gateway for Power BI or Fabric, you already know the model: a service on a machine in your network, outbound connections only, cloud queries answered from local data. Most concepts map one to one:

| Power BI on-premises data gateway | Timbal Connect |
| --------------------------------- | -------------- |
| Gateway machine | The server running Timbal Connect |
| Install, sign in with a work account, register the gateway and its recovery key | Install with a single-use [enrollment token](/api-reference/connectors/enrollment-tokens/create) |
| Data sources and their credentials added in the cloud, under **Manage connections and gateways** | Connections listed in [`connections.json`](/connect/connections) on the server; credentials stay there |
| **Network ports test** in the gateway app | The installer's network check and [`timbal-connect doctor`](/connect/troubleshooting#run-doctor) |
| Outbound TCP 443, 5671-5672 and 9350-9354 to several Microsoft domains | Outbound TCP 443 to `api.timbal.ai` only |
| Service account `NT SERVICE\PBIEgwService`, changed to a domain account or gMSA for Windows authentication | Service account `NT AUTHORITY\NetworkService`, [changed to a domain account or gMSA](/connect/connections#sql-server-authentication) the same way |
| Monthly releases you install yourself | Updates pushed by Timbal, rolled back automatically if the new version can't connect |

Two differences matter when you set it up:

- **Connections live on the server, not in the cloud.** There is no "add data source" screen in Timbal where you type a server name and password. You list connections in a file on the gateway server, and Timbal refers to them by name. Your database passwords are never stored in Timbal.
- **Some gateway features aren't available yet.** Timbal Connect can't go through an HTTP proxy: it needs direct outbound access to `api.timbal.ai` (see [Network requirements](/connect/network-requirements)). There are no gateway clusters either: each server is its own connector, and the queries and syncs you assign to a connector run only on that server.

## Before you start

<Steps>
  <Step title="Check the network">
    The server needs direct outbound HTTPS (TCP 443) to `api.timbal.ai`, with WebSocket allowed and no TLS inspection on that host. This is the most common blocker, so check it first: [Network requirements](/connect/network-requirements).
  </Step>
  <Step title="Get an enrollment token">
    Ask your Timbal contact for one, or create it with the API: [Create enrollment token](/api-reference/connectors/enrollment-tokens/create). The token is shown once and expires after 24 hours unless you set `ttl_secs` (up to 30 days).
  </Step>
  <Step title="Install">
    Follow the guide for your server: [Windows](/connect/install-windows) or [Linux and macOS](/connect/install-linux-macos).
  </Step>
  <Step title="Add your connections">
    Tell the connector which databases and file shares it may use: [Configure connections](/connect/connections).
  </Step>
</Steps>
