Self-hosting means you run the same three layers a `timbal create` project contains — **UI**, **API**, and **workforce** — without `timbal start` managing them. You own process lifecycle, port allocation, env wiring, restarts, and log aggregation.

The CLI does not build a container image. You bring your own process manager (systemd, supervisord, Kubernetes, etc.) and production build pipeline.

## Prerequisites

- A project created with [`timbal create`](/quickstart#create-a-timbal-project)
- [Bun](https://bun.sh) for `api/` and `ui/`
- [uv](https://docs.astral.sh/uv/) for workforce Python deps
- `timbal[server]` installed in each workforce member's venv

## What `timbal start` does (that you must replicate)

`timbal start` is the reference implementation. When self-hosting, reproduce the same wiring:

### 1. Workforce members

For each `workforce/<name>/` with a `timbal.yaml`:

```bash
cd workforce/<name>
uv sync
uv run -m timbal.server.http --port <port> --import_spec <fqn>
```

`<fqn>` comes from `timbal.yaml` (e.g. `agent.py::agent`). The HTTP server exposes:

```http
POST http://localhost:<port>/run      # collect (returns final OutputEvent)
POST http://localhost:<port>/stream   # SSE event stream
GET  http://localhost:<port>/healthcheck
GET  http://localhost:<port>/meta
```

`GET /meta` returns `{"version", "capabilities"}`. `capabilities` is `["context.tool_policy", "context.require_new"]`. `GET /healthcheck` is still `204`, with the same facts in `X-Timbal-Version` and `X-Timbal-Capabilities` (`context.tool_policy,context.require_new`).

### Request context

`POST /run` and `POST /stream` take an optional `context` object (`run_context` is the same key):

```json
{
  "prompt": "Summarize my open tickets",
  "context": {"id": "routine-1", "tool_policy": "read_only", "require_new": true}
}
```

`context.id` chooses the run id. One a running run already holds is `409`.

`context.tool_policy` narrows the tools every agent in the run offers its model. That includes subagents, an agent a tool or step starts, and one a background tool starts after the spawning run has ended.

- `"read_only"` — tools declared [`read_only`](/agents/tools#read-only-tools), MCP tools whose server sets `readOnlyHint`, and the agent's own readers.
- A list of tool names. The name matches in every agent of the run, and `[]` offers none.
- `null` — every tool. This is the default, and so is leaving the key off.
- Anything else is `400`.

A call to a tool the policy hid comes back as `tool_not_found`. A run that applied a policy confirms it with `X-Timbal-Tool-Policy: read_only`, `names` (`names` is any list, including an empty one), or `custom` (a resume that kept a paused run's policy that was not one of those, such as a chat session's). `null` sends no such header.

A resume (`resume` with `context.parent_id`) that leaves `tool_policy` out keeps the policy of the paused run it continues, so an approval cannot widen a read-only routine. Name one on the resume to change it: `null` gives every tool. If the paused run cannot be read (a tracing provider error), the resume is a `503` with `Retry-After`, and no run starts: retry it, or name `tool_policy`.

`context.require_new` must be a boolean (`400` otherwise). `true` refuses with `409` an id this process still remembers, finished runs included, for the job retention window (default 5 minutes; a restart forgets them). That is the safe retry after a lost response. Without it, reusing a finished id starts another run under that id, and a client still reading `GET /runs/{run_id}/events` for the old run follows the new one.

An Agent also exposes `/voice`, `/voice/ws`, and `/voice/rtc`. Install `timbal[server,voice]` for browser voice and WebRTC, or add `voice-livekit` for LiveKit rooms. Voice connections are long-lived: configure WebSocket upgrades, connection timeouts, and the appropriate media networking in your reverse proxy. See [Voice transports](/voice/transports) for carrier routes and ICE/TURN configuration.

### 2. API

```bash
cd api
bun install
PORT=<api_port> bun run dev    # dev; use your production start command in prod
```

### 3. UI (if present)

```bash
cd ui
bun install
bun run dev --port <ui_port>   # dev; use your production build/serve in prod
```

### 4. Cross-service env vars

The API and UI need to know where workforce members live. `timbal start` injects these — set them yourself when self-hosting:

| Variable | Example | Purpose |
|----------|---------|---------|
| `TIMBAL_START_WORKFORCE` | `a1b2c3d4-...:4455,b5c6d7e8-...:4456` | Manifest `_id` → port map (comma-separated) |
| `TIMBAL_START_API_PORT` | `3000` | API port (for services that call back to API) |
| `TIMBAL_START_UI_PORT` | `3737` | UI port |
| `PORT` | per-service | Port each Bun service binds to |

`TIMBAL_START_WORKFORCE` uses the `_id` from each member's `timbal.yaml`, not the directory name.

Also pass through model keys and integration secrets (`OPENAI_API_KEY`, etc.). Locally, `timbal start` auto-loads `<project>/.env` and `workforce/<name>/.env` into each process; when self-hosting you must export or inject those variables yourself (e.g. via your process manager or a secrets store). See [Environment variables](/deployment#environment-variables).

<Warning>
If any of `TIMBAL_START_*` are missing, platform SDK helpers that resolve service URLs will fail. Mirror what `timbal start` sets before debugging routing issues.
</Warning>

## Production considerations

### Process management

Run each component under a supervisor that restarts on crash:

- One process per workforce member
- One for API
- One for UI (if used)

Use health checks against `/healthcheck` on workforce HTTP servers. The response stays `204` and carries `X-Timbal-Version` and `X-Timbal-Capabilities`. Check those before an unattended run: an older server ignores `context.tool_policy` instead of refusing it.

### Logging

`timbal start` multiplexes stdout/stderr into one terminal with per-service prefixes and `f`/`m` focus controls. Self-hosted, you need your own approach:

- Separate log files or streams per component
- Structured logging if shipping to Datadog / CloudWatch / etc.
- Correlate by request ID if the API fans out to multiple workforce members

### Networking

- Put a reverse proxy (nginx, Caddy, etc.) in front of UI and API for TLS
- Workforce members can stay internal — only the API needs to reach them
- Lock down ports so workforce HTTP servers aren't exposed publicly

### Builds

The scaffold uses `bun run dev` for API/UI. For production, use whatever production build your scaffolded `api/` and `ui/` packages define (static UI build + API server, etc.). The workforce side stays `uv run -m timbal.server.http` with a pinned `uv sync` environment.

### Observability

Platform tracing still works from self-hosted runtimes — configure a [tracing provider](/core-concepts/tracing) to export spans to Timbal or your own OTLP endpoint.

## When to self-host

Self-hosting makes sense when you need full control over networking, data residency, or custom orchestration. For most teams, the [Timbal Platform](/deployment/platform) is less operational overhead — same project layout, no component wiring to maintain.
