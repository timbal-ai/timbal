Events stream execution notifications such as starts, content deltas, pauses, and completion. They do not themselves persist conversation memory. Applications can consume or record them, and the HTTP job store and background-task APIs retain bounded event logs. Traces capture span input, output, errors, timing, and usage through the configured tracing provider.

## Traces

A Trace is the core data structure that captures execution information for every runnable execution, providing a complete audit trail of what happened. This tracing system enables complete observability into your application's behavior and performance.

For the previous LLM example, a single **span** inside the run's trace would look like this:

```python
from timbal.state.tracing.span import Span

llm_span = Span(
    path="agent.llm",
    call_id="068c4458383678be800031537a8df42e",
    parent_call_id="068c4458382e708f8000cc0f9b19d970",
    t0=1640995200000,  # Start time (Unix ms)
    t1=1640995201000,  # End time (Unix ms)
    input={
        "model": "openai/gpt-4o-mini",
        "messages": [{
            "role": "user",
            "content": [{"type": "text", "text": "Hello"}],
        }],
    },
    output={
        "role": "assistant",
        "content": [{"type": "text", "text": "Hello! How can I assist you today?"}],
    },
    usage={
        "openai/gpt-4o-mini:input_text_tokens": 32,
        "openai/gpt-4o-mini:output_text_tokens": 10,
    },
    metadata={
        "type": "LLM",
        "model_provider": "openai",
        "model_name": "gpt-4o-mini",
        "ttft": 1.218775834015105,  # Time To First Token
        "tps": 103.44992571967803,  # Tokens Per Second
    },
)
```

Spans are stored in a `Trace` — a dict keyed by `call_id`. Access them during or after a run via `get_run_context()._trace` or helper methods like `step_span()`.

That's a single span, but spans don't usually come in isolation — they're organized into larger execution units: Runs.

## Runs

A Run represents the complete execution of your application - from the moment you invoke a runnable until it finishes. Think of it as the lifecycle of a single request or operation, whether that's a simple function call or a complex multi-step agent workflow.

Every Run is composed of a collection of spans:

- **Simple execution**: Running a single tool generates one span — the tool's input, output, timing, and metadata
- **Complex execution**: Running an agent generates multiple spans as it decides which tools to use, calls LLMs for reasoning, executes tools, and processes results

All spans within a run share the same `run_id` (via `RunContext.id`), creating a complete execution history that you can analyze, debug, or replay.

### The Run Context

Traces are stored in the RunContext - a central hub that manages all run data. You can access traces during execution, control storage behavior, and use this system to share data between different parts of your run.

More on this in the [Context](./context) section.

### Save durability

A finished span asks the provider to save. What the run waits for is that provider's durability.

`sync` awaits every save. `buffered` stores a save while the run is going in the background and coalesces saves that pile up in between. The run waits at its end, including a pause for approval, and at other barriers: handing a task to the background, the end of that task, and shutdown. A crash can lose at most `max_lag_s` of mid-run progress (default 30 seconds). Past that lag, saves are awaited again until one succeeds. `end` skips saves while the run is going and stores only at those same barriers, so a crash loses everything since the last one.

The mode is `configured(durability=...)`, then `TIMBAL_TRACE_DURABILITY`, then the provider default: `buffered` for `PlatformTracingProvider`, `sync` for the others. Any other value is read as `sync`. `PlatformTracingProvider.configured(durability="sync")` or `TIMBAL_TRACE_DURABILITY=sync` awaits every platform save again. `configured(flush_interval_s=...)`, in seconds, and `configured(max_lag_s=...)` override the two timing variables.

- `TIMBAL_TRACE_FLUSH_INTERVAL_MS`: minimum milliseconds between background saves of one run. Default: `500`.
- `TIMBAL_TRACE_MAX_LAG_S`: how old the oldest unsaved change may get, in seconds, before saves are awaited again. Default: `30`.
- `TIMBAL_TRACE_METRICS`: set to `1`, `true`, or `yes` to add `tracing:*` usage keys. Setting durability explicitly to `buffered` or `end` adds them as well. The platform default does not.

### When a save fails

Each finished span requests a save. With the platform default that mid-run save is not awaited: it is stored in the background and coalesced, and the run waits at its end and at other barriers. A crash can lose up to 30 seconds of that progress; past that, the save is awaited. If the provider fails to store a snapshot, for example the platform rejecting a run whose parent it has no record of, or an outage that outlasts the retries, the run still completes and returns its output. The failure is logged as an error. An awaited save is counted as `tracing:save_failed` in the run's usage. A background save counts that failure only when tracing metrics are on. Cancellation is not caught.

## Platform trace cache

`PlatformTracingProvider` caches traces this process successfully saves, so a following agent or workflow run can load its parent's trace without another platform request. This also applies to voice turns. The cache holds up to 256 distinct runs and 64 MiB of serialized traces across the process by default; saving the same run again replaces its snapshot and refreshes its expiry. A failed save drops that run's cached snapshot, so the next read goes to the platform. When saves of the same run overlap, the most recently taken snapshot decides what is cached, whichever request finishes last, even if its cached copy has since been evicted.

Configure the cache with environment variables:

```bash
export TIMBAL_TRACE_CACHE_MAX_ENTRIES=64
export TIMBAL_TRACE_CACHE_TTL_SECS=60
```

- `TIMBAL_TRACE_CACHE_MAX_ENTRIES`: maximum number of cached runs, a non-negative integer. Default: `256`.
- `TIMBAL_TRACE_CACHE_TTL_SECS`: seconds since the last successful save, a non-negative finite number. Default: `300`. Reading a trace does not extend its lifetime.

Setting either value to `0` disables caching and clears existing entries on the next cache access. Invalid values produce one warning per distinct value and fall back to the corresponding default. Settings are read on each cache access.

- `TIMBAL_TRACE_KEEPALIVE_SECS`: while a run is in flight, save it again after this many seconds without a save, so the platform does not treat it as dead. Default: `300`. `0` disables it. `PlatformTracingProvider.configured(keepalive_s=...)` overrides the variable. The timer starts from a save and is dropped once the run has ended, so a run that does not save until its end is not kept alive.
- `TIMBAL_TRACE_KEEPALIVE_MAX_SECS`: stop those keep-alives after this many seconds without a save the run made for itself. A keep-alive does not reset the clock. Default: `14400` (4 hours).
- `TIMBAL_TRACE_FLUSH_TIMEOUT_SECS`: one bound, in seconds, for the shutdown flush of buffered uploads and for `PlatformTracingProvider.flush()`. Default: `5`.

Cache reads and writes remove expired entries, including entries for other runs. Cleanup is lazy: an idle process retains entries until the next cache access. When either limit is exceeded, the least recently saved runs are evicted; a single trace larger than the byte limit is not cached. Eviction only removes the local copy; traces remain stored on the platform, and cache misses fetch them there. Traces fetched from the platform are not added to this cache.

A read of a run this process is still saving waits up to 2 seconds for saves already asked for, with or without the cache: a save on the wire, and one queued behind it. A buffered save is included once the provider has been asked to store it, not while it is still waiting out its flush interval. When the wait ends, the platform may still answer 404 or an older snapshot. This covers a voice turn whose save is still on the wire when the next turn starts.

Entries are scoped by host, organization, app, token, and run ID, and each read returns an independent copy. Updates made by another process can remain invisible until the cached entry expires or is evicted; lower the TTL or disable caching when those updates must be visible immediately.
